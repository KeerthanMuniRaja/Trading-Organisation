## Version 0.3 — 3 October 2026

The owner supplied the financial model and accepted the suggested management principles. This update records that agreement while keeping the project in brainstorming.

### Added

- A wallet and treasury policy: all owner deposits go to Wallet 1, Wallet 2 starts at zero, and eligible realised net profit is allocated 60%/40%.
- Explicit separation between bots, shared capital control, restricted profit distribution, and owner-authorised transfers.
- Cumulative loss recovery and a proposed allocation-history calculation that prevents allocating the same profit twice.
- Settlement, shared reservations, pending-transfer reporting, and recovery rules for financial obligations.
- A worked loss-and-recovery example, owner-transfer examples, 22 proposed acceptance scenarios, and a financial reconciliation template.
- A financial knowledge-graph diagram and relationships connecting contribution provenance, allocation, approval, transfer, and budgets.

### Agreed management principles

Independent financial controls; departmental budgets and measurable value; retained profit as available capital rather than a spending target; defined operating-cost treatment; shared spending reservations; predetermined loss responses; and owner financial reporting.

### Clarified status

The earlier blanket deferral of wallet design is superseded. Custody, payout feasibility, distribution timing, detailed costs, taxes, reserves, rounding, numerical limits, and implementation remain open. No account, transfer, trade, deployment, or spending has been enabled.

This version contains 24 Markdown documents and five Mermaid diagrams. Versions 0.1 and 0.2 are retained. The scenarios are design specifications and worked arithmetic, not successful tests of a deployed financial application.

## Version 0.2 — 3 October 2026

Historical entry: the wallet deferral below describes version 0.2 and is superseded by version 0.3.

This update consolidates the discussion after the original ZIP and the latest R&D lifecycle requirements.

### Added

- Hermes Agent and Ruflo to the reference set, with source links, proposed roles, overlap, and review limitations.
- A dedicated document on self-hosted operation, retained dependencies, and the distinction between repository availability and runtime services.
- A dedicated recovery and notification document: detect, contain, diagnose, repair, verify, resume, learn, and escalate when necessary.
- A full R&D lifecycle for new bots, education, graduation, differentiated work, hackathons, departmental growth, and retirement.
- Knowledge-graph relationships for inherited skills, distinct contribution, fitness, recovery, dependencies, and verified transfer.
- Templates for bot/department proposals, graduation, hackathons, and knowledge transfer/retirement.

### Clarified

- Open-source reuse is accepted; the owner did not require excluding all open-source infrastructure.
- Frameworks, models, and hosted APIs are different kinds of dependency.
- A new bot can inherit useful knowledge while still needing to demonstrate its own contribution.
- Replication may support a proven opportunity, workload partition, or independent verification; redundant output is not a new capability.
- Fitness is role-specific and includes contribution to the organisation. Support departments need not directly generate trading revenue.
- Revenue-linked growth is an objective; the financial formulas and wallet design are explicitly deferred.
- Useful knowledge and accountability records should survive retirement. Incorrect or unverified content must remain labelled.
- Recovery must be verified and reported; no guarantee of fault-free operation or universal autonomous repair is made.

### Updated

README, requirements, department map, knowledge graph, daily research process, learning/evaluation, governance, repository map, roadmap, and all four original templates.

### Package status

Version 0.1 is preserved. This package contains 21 Markdown documents and four Mermaid diagrams. It remains a brainstorming record, not an implementation, deployment, account connection, or scheduled automation.
